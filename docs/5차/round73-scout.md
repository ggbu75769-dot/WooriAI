# 라운드 73 정찰 노트 (GAP-073)

> 대조 완료. 아래는 전부 그 밖이거나, 라운드 72가 접점으로 남긴 잔여다.
>
> **이번 라운드는 축을 앱 안에서 앱 밖으로 옮긴다.** 라운드 72의 코드 건강 판정은 "여정의 끝"에
> 이어 "여정의 시작"까지 훑었다고 적었고, 이번 정찰이 앱 전역을 다시 훑어 새로 찾은 **인앱
> 정직성 결함은 후보 5의 네 줄뿐**이다(그마저도 목록 하나가 없어서 남은 꼬리다). 그런데 이
> 저장소가 72라운드 동안 **한 번도 스윕 단위로 삼지 않은 표면**이 있다 —
> **사용자가 앱을 설치하기 *전에* 보는 것**(스토어 등록 정보·스크린샷)과 **앱 없이 보는
> 것**(공유된 구매 링크가 떨어지는 페이지·초대 랜딩·지원 사이트·약관), 그리고 **그 빌드를
> 만드는 파이프라인**이다. 오늘 재어 보니 그 셋 전부가 **앱과 다른 것을 보여 주고 있었다**.
>
> **두 번째 축은 어드민·서버 운영 품질**이다(모회의 제안 축). 어드민은 라운드 43·63·64가
> 기능을 채웠지만 **실패했을 때 무엇을 말하는가**는 한 번도 스윕된 적이 없다 — 오늘 세어 보니
> 조회 실패 자리 **열다섯 중 열이 이유를 통째로 버린다**. 모바일이 라운드 38~72에 걸쳐 없앤
> 그 결함이 어드민에는 그대로 있다.
>
> **성능·용량 축은 이번에 제안하지 않는다.** 실측했고 근거가 나오지 않았다(선행 확인 6).
> **테스트 인프라 축도 제안하지 않는다** — 스위트 시간을 실행 없이 잴 수 없고, 구조만 재어
> 보면(선행 확인 7) 오히려 건강하다. 실측 없는 제안은 하지 않는다.

## 상위 후보

### 1. **스토어에 올릴 빌드가 개발 빌드처럼 말하고, 그것을 막을 관문이 없다** — 실사용자가 보는 첫 화면 — M

- **근거**: 넷이 한 줄로 이어져 있다.
  - ⓐ **로그인 실패 문구의 갈래 기준이 틀렸다.** `app/(auth)/login.tsx:246-250`:
    ```
    setLoginError(
      isKakaoLoginAvailable()
        ? "로그인 중 문제가 발생했어요. 네트워크 연결을 확인한 뒤 다시 시도해 주세요."
        : "서버에 연결할 수 없어요. PC와 같은 Wi-Fi에서 API 서버가 켜져 있는지 확인해 주세요."
    );
    ```
    `isKakaoLoginAvailable()`은 **env가 주입됐는가**만 본다(`src/auth/kakao-login.ts:109-111` —
    `getKakaoEnvConfig() !== null`). "PC와 같은 Wi-Fi" 문장은 개발 스텁 경로를 위한 것인데,
    그 갈래를 여는 조건이 **빌드 종류가 아니라 env 부재**라서 **카카오 키 없이 만든 스토어
    빌드에도 그대로 실린다.**
  - ⓑ **그 빌드에서 실제로 무슨 일이 벌어지는지도 확인했다.** `login.tsx:184`는
    `isKakaoLoginAvailable() ? loginWithKakao() : oauthLogin("kakao")`이고,
    서버의 `oauthLogin`은 프로덕션에서 **501로 fail-closed**다
    (`apps/api/src/auth/auth.service.ts:25-32` — `OAUTH_LOGIN_NOT_IMPLEMENTED`). 그 코드는 앱의
    화이트리스트에 없으므로 위 삼항까지 그대로 떨어진다. 즉 **"카카오로 시작하기"를 누른
    실사용자가 받는 답은 "PC와 같은 Wi-Fi에서 API 서버가 켜져 있는지 확인해 주세요."**다.
  - ⓒ **AAB 빌드가 그것을 막지 않는다.** `scripts/build-android-aab.ts:42-75`의 `validateEnv()`가
    fail-closed로 요구하는 것은 keystore 넷 · 패키지·버전 셋 · `EXPO_PUBLIC_API_BASE_URL`
    하나뿐이다. **카카오 셋도, 약관·개인정보 URL 둘도, 지원·FAQ URL 둘도 묻지 않는다.**
    `buildChildEnv`(`:77-93`)는 `...process.env`를 펼치므로 값이 있으면 실리지만, **없어도
    빌드는 끝까지 성공한다.** API 주소 하나만 "없으면 조용히 localhost가 실린다"는 이유로
    fail-closed인데(그 주석이 근거를 적어 뒀다), 나머지 일곱은 같은 성질인데도 침묵한다.
  - ⓓ **env 카탈로그가 앱이 읽는 키를 다 세지 않는다 — 드리프트 가드에 사각이 있다.**
    `scripts/check-env.ts`의 드리프트 가드(`:243-283`)는 **카탈로그 ↔ `.env.example`
    양방향만** 본다. **소스는 한 번도 읽지 않는다.** 그래서 코드가 읽는데 카탈로그에도
    `.env.example`에도 없는 키는 **어느 쪽에서도 보이지 않는다** — 오늘 그런 키가 둘이다:
    `EXPO_PUBLIC_SUPPORT_URL` · `EXPO_PUBLIC_FAQ_URL`(라운드 71 D가 넣었다.
    읽는 자리는 `src/settings/support-links.ts:52-53`, 값은 `infra/site/README.md:82-83`이
    문서화했다). `INTENTIONALLY_UNCATALOGUED`(`:139-146`)는 **`.env.example` 쪽 방향에만**
    참여하므로 이 둘을 구제하지도, 드러내지도 않는다.
  - ⓔ **배포가 만드는 env도 아무도 읽지 않는다.** `scripts/deploy/oracle-bootstrap.sh:132-158`이
    `.env.production`을 생성하는데, 카카오 셋은 **주석**이고(`#OAUTH_KAKAO_CLIENT_ID=`),
    `LINK_HEALTH_ENABLED`는 **한 줄도 없다**(기본 0). 그리고 그 파일을 `pnpm check:env`에
    통과시키는 경로가 저장소에 **없다** — 릴리즈 게이트는 `.env`/`.env.example`만 본다.
    `WORKER_ENABLED`에는 "**끌 때도 0을 명시**"라는 규율이 카탈로그에 적혀 있는데
    (`check-env.ts`), 정작 배포가 만드는 파일은 그 규율 밖이다.
- **실패 시나리오**: 출시일이다. 운영자가 `pnpm android:build-aab`를 돌린다 — keystore·패키지·
  버전·API 주소를 넣었으니 **빌드가 성공한다.** Play에 올리고 심사가 통과한다. 첫 사용자가
  앱을 깔고 연다. 스플래시가 지나고 **"카카오로 시작하기"**가 보인다. 필수 동의 둘을 체크하는데
  [보기] 링크가 없다(URL 미주입 — 정직한 감춤이다, 다만 **읽지 못한 문서에 동의**하게 된다).
  버튼을 누른다. 브라우저가 뜨지 않고 카드 한 줄이 뜬다:
  **"서버에 연결할 수 없어요. PC와 같은 Wi-Fi에서 API 서버가 켜져 있는지 확인해 주세요."**
  이 사람에게는 PC도 API 서버도 없다. 몇 번 더 누르고 앱을 지운다. **이 앱은 첫 화면에서
  개발자에게 말을 걸었고, 그 빌드를 만든 파이프라인은 아무것도 묻지 않았다.**
- **최소안**: **"실사용자 빌드가 되기 위해 무엇이 필요한가"를 값으로 세운다.**
  ⓐ **빌드 성격 판정을 한 자리에** — `isDeveloperBuild()` 같은 술어 하나
  (`src/auth/release-build.ts` 신설 또는 `login-copy.ts` 합류)를 만들고, "PC와 같은 Wi-Fi"
  문장은 **그 술어가 참일 때만** 선다. 개발 빌드의 문장은 **바이트 단위로 종전 그대로**이고,
  실사용자 빌드는 위 삼항의 첫 갈래(종전 문장)를 받는다 — **새 문구 0건**이다.
  ⓑ **AAB가 fail-closed로 묻는다** — `validateEnv()`에 "실사용자 빌드가 갖춰야 할
  `EXPO_PUBLIC_*` 목록"을 **한 자리 값**으로 세우고(키마다 "없으면 사용자가 무엇을 잃는가"
  한 줄), 없으면 API 주소와 **같은 형식으로** 거부한다. ⚠️ 강제와 선택을 나눈다: 카카오 셋과
  약관·개인정보 둘은 **없으면 앱이 오동작하거나 읽지 못한 문서에 동의시키므로 필수**,
  지원·FAQ 둘은 **명시적 opt-out 플래그로만** 통과시킨다(그때 "앱 안에 도움으로 가는 길이
  0건인 채로 나갑니다"를 출력한다 — L-3이 예고한 그 상태를 침묵으로 두지 않는다).
  ⓒ **드리프트 가드에 세 번째 방향을 더한다** — `apps/mobile/{app,src}`가 읽는
  `process.env.EXPO_PUBLIC_*`을 전수로 긁어, 카탈로그나 `INTENTIONALLY_UNCATALOGUED`에
  없으면 빨개진다. 그 김에 `EXPO_PUBLIC_SUPPORT_URL`·`EXPO_PUBLIC_FAQ_URL`을 카탈로그와
  `.env.example`(오늘 `:86-87` 아래)에 넣는다.
  ⓓ **배포가 만드는 파일이 침묵하지 않는다** — `oracle-bootstrap.sh`의 heredoc이

## 코드 건강 판정

- **인앱 정직성 광맥은 실제로 얇아졌고, 이번에 남은 넷은 "목록이 없는 쪽"에 있었다.**
  라운드 72가 조회 실패 목록을 열까지 밀면서 그 축을 사실상 닫았는데, **저장 실패 쪽에는
  목록 자체가 없어서** 아무도 세지 않았다(계약이 두 경로를 손으로 적은 배열이다). 라운드 71 L-1이
  "여정 목록이 없다", 라운드 72 M-3이 "상황 목록이 없다"고 적은 것과 **정확히 같은 층의
  사각이 한 칸 옆으로 옮겨간 것**이다. 이 저장소에서 결함이 살아남는 방식은 이제 거의 언제나
  **"세는 목록이 없다"** 하나다. 다음 라운드가 물어야 할 것은 "**아직 목록이 없는 축이 무엇인가**"다.
- **72라운드 동안 스윕 단위가 된 적 없는 표면이 셋 있었고, 셋 다 앱 밖이다.**
  ① 설치 **전** 접점(스토어 자산) ② 앱 **없이** 보는 접점(공유 링크 실패 페이지·초대 랜딩·
  지원 사이트·법적 문서) ③ 그 빌드를 만드는 **파이프라인**. 이 저장소의 규율("확인하고 말한다",
  "지어내지 않는다", "정직한 부재")은 앱 안에서 대단히 성숙했는데, 그 규율이 앱 경계에서 멈춘다.
  오늘 그 셋을 재어 보니 **팔레트가 네 벌**(앱 `#C94627` · 스토어 자산 `#DB4F2E` · 공개 HTML
  `#FF7A59` · 정적 사이트/법적 문서 `#FF8A7A`)이고, 스토어 스크린샷은 **DSN-053 이전 빌드**이며,
  릴리즈 스크립트는 **API 주소 하나만** 묻는다. 결함의 성격이 인앱과 다르다 —
  인앱은 "앱이 틀린 말을 한다"였는데 여기는 "**앱 밖이 다른 앱을 보여 준다**"다.
- **어드민은 "판정 없음"이 아니라 "판정을 안 읽음"이다.** `admin-api.ts`는 타임아웃을 읽기/쓰기로
  나누고 멱등 여부까지 갈래를 만들며, `worker-health-view.ts`는 "0건 = 확인 안 됨"을 값으로
  적었다. 그런데 그 판정을 소비하는 화면은 각각 **넷**과 **하나**뿐이다. 모바일이 라운드 38~72에
  걸쳐 배운 것("판정은 한 벌, 문구는 화면별, **그리고 목록이 그 소비를 센다**")이 어드민에는
  아직 도착하지 않았다. 후보 4의 계약이 파일이 아니라 **소비 집합**을 세는 형태여야 하는 이유다.
- **실측해서 기각한 축 둘을 값으로 남긴다.** 성능·용량(선행 확인 6)과 테스트 인프라(선행

  성능이 아니라 **경계**에 쌓여 있다. 다음 라운드가 같은 축을 다시 파지 않도록 오늘의 수치를
