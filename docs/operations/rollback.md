# 롤백 절차

## 1. API 서버 롤백

1. 이전 릴리즈 커밋/태그로 배포 대상 전환.
2. **마이그레이션 호환성 확인**: 롤백 대상 코드가 현재 DB 스키마와 호환되는지 확인한다. 대부분은 additive(테이블·컬럼·색인 추가)라 코드만 롤백해도 안전하지만 **전부는 아니다** — 예외 다섯은 아래 §1.1이 값으로 진다.
   - ⚠️ **두 시점**: 이 줄은 종전에 "**라운드 4 마이그레이션**은 additive 위주라 코드만 롤백해도 대체로 안전하다"라고 적었다. **그때는 참이었다** — 라운드 4가 낳은 것은 `000002`~`000005` 넷이고 그 넷은 실제로 그렇다. 오늘(2026-09-07) 마이그레이션은 `000001`~`000025`이고, 라운드 4 뒤에 붙은 스무 개에 대해 이 문서는 종전까지 아무 말도 하지 않았다. 아래 표가 그 스무 개까지 전수로 읽은 결과다.
3. 스키마 롤백이 불가피하면 — Prisma는 down migration을 생성하지 않으므로 [database-backup-restore.md](database-backup-restore.md)의 배포 직전 백업으로 복원한다. **백업 이후 데이터는 유실되므로 최후 수단.** ⚠️ 그리고 그 백업이 추천 배포 경로에는 없다 — [incident-response.md](incident-response.md) §데이터 사고 4번.
4. 재기동 후 `GET /api/v1/health/ready`가 200인지 확인.

### 1.1 롤백 성질 표 (`000001`~`000025` 전수, 2026-09-07 다시 읽음)

판정 기준 둘: **ⓐ 코드만 되돌려도 안전한가**(구 빌드 + 신 스키마) · **ⓑ DB를 되돌릴 수 있는가**.
개수는 이 표가 세지 않는다 — 마이그레이션의 단일 소스는 `apps/api/prisma/migrations/` 디렉터리다.

| 묶음 | ⓐ 코드만 롤백 | ⓑ DB 롤백 | 판정 |
|---|---|---|---|
| `000001_init` (표 19 + enum + CHECK + 리포트 뷰) | 해당 없음 — 이 아래로는 되돌릴 코드가 없다 | 해당 없음 | 롤백 대상이 아니다 |
| 색인만 더한 것 (`000011`·`000012`·`000014`~`000017`·`000021`·`000025`) | 안전 | 안전(색인 드롭) | **완전 가역** |
| 표·컬럼을 더한 것 (`000002`~`000004`·`000006`·`000009`·`000013`·`000019`·`000020`·`000022`·`000023`) | 안전 — 구 코드는 새 칸을 모른다 | 드롭하면 **그 기능의 사용자 데이터가 사라진다**(커스텀 품목·카테고리 예산·패밀리 만료 기준 등) | 코드 롤백 OK · DB 롤백은 데이터 손실 |
| `000005` (`import_rows.validation_status` 길이 확장) | 안전 | 좁히면 값 절단 위험 | 코드 롤백 OK |
| **`000007`** · **`000008`** · **`000010`** · **`000018`** · **`000024`** | 아래 | 아래 | ⚠️ **롤백 안전지대 없음** |

⚠️ **되돌릴 수 없는 다섯.** 종전 이 문서는 이 자리를 비워 두었고, 저장소 안에서 롤백 성질을
스스로 적어 둔 마이그레이션은 `000024` 하나뿐이었다(그 파일 머리말 참고). 나머지 넷도 같은
성질이다:

- **`000007_round5_cms_oauth_analytics` — 밖으로 나간 코드는 되돌릴 수 없다.**
  `product_links.redirect_code`를 난수로 backfill한 뒤 NOT NULL + UNIQUE를 건다. 그 코드는
  **공개 리다이렉트 URL(`/api/v1/r/:code`)의 일부**로 앱의 공유 구매 링크와 어드민 공유 URL을
  통해 밖으로 나간다. 컬럼을 드롭하고 다시 만들면 `DEFAULT substr(md5(gen_random_uuid()::text),1,12)`가
  **새 난수를 뽑으므로, 이미 나간 모든 링크가 영구히 404**가 된다. 코드만 되돌리는 것은 안전하다.
- **`000008_affiliate_clicks_nullable_actor` — 코드만 되돌리는 것이 안전하지 않다.**
  `affiliate_clicks`의 `user_id`·`household_id`·`child_id` 셋에서 NOT NULL을 **푼다**. 비로그인
  클릭이 한 건이라도 쌓인 뒤에 구 빌드로 되돌리면 구 Prisma 클라이언트가 그 칸들을
  non-nullable로 타이핑하므로 집계·어드민 조회가 null을 만나 깨진다. DB 롤백(NOT NULL 재부착)은
  **그 행들 때문에 실패한다**. 이 하나가 "additive 위주라 대체로 안전"의 반례다.
- **`000010_user_devices_unique_token` — 유일하게 데이터를 지우는 마이그레이션.**
  유니크 인덱스를 걸기 전에 중복 `user_devices` 행을 `DELETE`한다. **빈 운영 DB에는 무해**하고
  신규 배포에는 해당이 없지만, 이미 데이터가 있는 DB(기존 dev/스테이징을 승격하는 시나리오)에
  처음 적용하는 순간 지워진 행은 **되돌릴 방법이 없다**.
- **`000018_categories_selectable` — 구 클라이언트에 하위 호환이 아니다.**
  `GET /categories` 기본 응답이 21행 → 12행으로 **줄어드는** 변경이다(필드 추가가 아니다).
  구 앱은 별칭·스텁 행을 못 받아 칩 매칭·라벨이 무너진다. 그래서 **API와 앱은 같은 사이클로**
  배포하고, 롤백도 한쪽만 되돌리면 안 된다(경위는 [known-limitations.md](known-limitations.md)
  "배포 결합 주의(R26 리뷰)", `docs/5차/launch-72h-plan.md` §2.1).
- **`000024_categories_household_owner` — 이미 문서화돼 있다.** 그 마이그레이션 파일 머리말이
  ①코드만 롤백(가구 간 커스텀 분류 이름 노출) ②컬럼 드롭(소유자만 사라져 시드와 구별 불가)
  둘 다 위험한 이유를 적는다. **"DB를 먼저 되돌린다"가 아니라 "앞으로 고쳐 나간다"로 계획한다.**

**앞으로의 관례**: `000024`가 이미 하고 있듯 **마이그레이션 파일 머리말에 롤백 성질을 한 줄**
적는다. 그러면 이 표가 다음 라운드에 다시 낡지 않는다(표는 사본이고, 원본은 각 SQL 파일이다).

## 2. 모바일 앱 롤백

- 스토어 배포 전 단계이므로 이전 APK 아티팩트(artifacts/android/)를 재배포하면 된다.
- 스토어 배포 후에는 Play Console의 단계적 출시 중단 → 이전 버전 재출시. 서버 API는 하위 호환을 유지해야 한다(응답 필드 제거 금지).

## 3. 관리자 CMS 롤백

- API와 함께 롤백. 레거시 x-admin-token 경로는 production에서 항상 차단이므로 롤백 후에도 관리자 JWT 로그인이 필요하다.

## 4. 롤백 판단 기준

즉시 롤백: 로그인 불가, 지출 저장 실패율 급증, 데이터 정합성 오류(홈≠리포트), readiness 연속 실패.
수정 후 배포(롤백 불필요): 특정 화면 UI 결함, 통계 지연.

## 5. 롤백 후 조치

- 원인 회귀 테스트 추가 전까지 재배포 금지.
- `audit_logs`·서버 로그로 영향 사용자 범위 파악, [incident-response.md](incident-response.md) 절차 수행.
