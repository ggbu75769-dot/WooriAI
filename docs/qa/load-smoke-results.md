## 해석

- **가장 느린 엔드포인트는 GET /home** (p50 114ms, p95 251ms — 다른 GET 대비 2~3배).
  첫 번째 추정 원인(측정 당시 `OnboardingStoreService.getHome`): child 접근 검증 → budget 조회 → 지출 목록
  → 추천 아이템 → 예산 DTO를 **순차 await**로 실행하고, 특히 `expensesForChild(childId)`를 **두 번 호출**해서
  child의 전체 지출을 중복으로 읽는다. `Promise.all` 병렬화 + 지출 1회 조회 재사용만으로도 눈에 띌 여지가 있다.
  → **후속 조치 완료**: REF-118로 갓 서비스가 분해되어 이 메서드는 현재
  `apps/api/src/onboarding/reporting-store.service.ts`의 `ReportingStoreService.getHome`이며,
  PERF-103이 독립 조회를 `Promise.all`로 병렬화하고 PERF-121(F1)이 전량 조회를 SUM + LIMIT 3 두 쿼리로 대체했다.
  (위 수치는 그 이전 측정값이므로 현행 성능과 다르다.)
- 그 외 엔드포인트는 p50 40~80ms, p95 80~150ms 수준으로 dev 모드 치고 무난.
- /health/ready p99가 126ms로 튄 것은 동시성 10에서 이벤트 루프/DB 커넥션 경합에 의한 꼬리 지연으로 보임(단건 p50은 9.5ms).

### 판정

- **H절(홈 콜드 스타트 전량 조회): 지금 해소할 필요 없음.** 근거 — 비용이 페이지 수에 정직하게
  비례하고(1페이지 88ms → 11페이지 1384ms), H절이 증상 조건으로 든 "한 달 수백 건" 구간은
  여전히 **1페이지**라 100ms대다. 다만 **월 1,000행(3페이지)을 넘는 계정이 생기면 재검토**할 것:
  루프는 순차 왕복이라 실기기에서는 여기에 페이지당 RTT가 그대로 더해진다(로컬 루프백 측정에는
  그 항이 없다). H절이 적어 둔 해소 방향(기간 합계 엔드포인트)을 폐기하지 말고 그대로 둔다.
- **F절(깊은 커서): 이 조건에서 깊은 페이지가 첫 페이지보다 느리지 않다는 것까지 확인됨.**
  5,001행 중 마지막 꽉 찬 페이지를 여는 커서가 첫 페이지보다 오히려 빨랐다(155.7 vs 186.0ms).
  R24-M3 후속A(커서 술어에 `spent_on <=` 상한을 AND로 명시해 000017 인덱스 범위를 Index Cond로
  올린 것)가 실제로 동작한다는 뜻이다. F절 깊은 커서 항목은 현 상태 유지.
  - **이 수치가 지지하지 않는 것**: "위험 아님"은 이 표가 낼 수 있는 결론이 아니다. 잰 것은
    **볼륨 하나(5,001행) · 환경 하나(dev 모드 · 로컬 PG · 단일 컨테이너) · 측정 한 번**이고,
    깊이를 여러 단계로 훑거나(예: 2·5·10만 행) 동시 부하 아래에서 재 본 적은 없다. 위 §"재실행
    간 편차"가 보여 준 것처럼 이 환경의 절대값은 회당 수십 %씩 흔들린다. 그래서 판정은 "이
    조건에서 깊이 페널티가 관측되지 않았다"까지이며, 커서 술어가 3분기 OR로 나가는 구조 자체는
    그대로다(R24-L4/M3 절). 볼륨을 한 자릿수 더 키우거나 운영 환경에서 다시 잴 때 이 문장을
    갱신할 것.
- **델타 동기화**: 5,000행에서도 `limit=100` 한 페이지는 38ms — 페이지 크기가 상한이라
  볼륨에 둔감하다. 볼륨 위험은 델타가 아니라 위 전량 루프 쪽에 있다.

### 판정

- **셋 중 실제로 문제인 것은 어드민 목록 하나다.** 준비템이 62의 17배가 될 때 p50이 46배가 되고
  (29.9ms → 524.5ms) 응답 본문이 **2.26MB**가 된다. 3,062개에서는 1.4초 · 6.5MB다. 비용이
  준비템 수에 거의 선형이라(**≈+0.45ms/준비템 · +2.2KB/준비템**) 예측은 쉽고, 그래서 문턱도
  명확하다 — **응답 본문 1MB(≈준비템 500 · 링크 1,500)를 넘으면 페이지네이션·필터를 붙일 것.**
  지금 이 목록에는 `where`도 `take`도 없다. ⚠️ 이 축은 **실기기 체크표의 대상이 아니다**
  (어드민은 브라우저 화면 — 라운드 63이 세운 판정). 수치는 이 문서가 진다.
- **앱 축(준비템 탭 · 홈): 지금 해소할 필요 없음. 재검토 문턱은 활성 준비템 500건.** 근거 —
  비용이 카탈로그 크기에 정직하게 비례하고(**≈+0.11ms/준비템**), 지금 운영 중인 62개에서는
  27.9ms다. 500개에서 p50 ≈ 80ms(선형 외삽)이라 그 지점까지는 지금 구조로 버틴다. 넘으면
  다시 재고, 그때의 첫 후보는 **단계 필터를 DB로 내리는 것**이다(지금은 전량을 읽어 JS에서
  거른다 — `rankItemsForTab`). ⚠️ 로컬 루프백 측정이라 실기기에서는 여기에 RTT가 더해진다.
- **상세는 이 축과 무관하다는 것까지 확인됐다.** 카탈로그가 49배가 되는 동안 p50이 19.8 →
  19.5ms로 **불변**이었다 — 상세는 준비템 1건 + 그 준비템의 링크만 읽고, 링크 조회가
  `idx_product_links_item_platform`(item_template_id 선두)을 타기 때문이다. 준비템당 링크가
  수십 개가 되는 날에는 다시 재야 하지만, 카탈로그 **전체**가 커지는 것으로는 움직이지 않는다.
- **이 수치가 지지하지 않는 것**: ⓐ 잰 것은 **준비템:링크 = 1:3 한 모양**이다. 실 제휴 계약이
  들어와 인기 품목에만 링크가 몰리면(1:20) 어드민 본문은 이 표보다 빨리 커진다. ⓑ 상태 행은
  준비템 3개당 1개(대상 아이 기준)로만 심었다 — 오래 쓴 계정의 상태 행 비율은 이보다 높고,
  그 축은 `itemsForChild`의 두 번째 조회다. ⓒ 여전히 **dev 모드 · 로컬 PG · 단일 컨테이너**이고
  동시 부하 아래에서 재 본 적은 없다. ⓓ **이번 라운드는 재기만 했다** — 서버 최적화는 한 줄도
  하지 않았다(재기 전에 인덱스나 페이지네이션을 붙이면 무엇을 고쳤는지 증명할 수 없다는
  라운드 60 H절의 순서 그대로다).

## 재실행 방법

```bash
# 1. (필요시) postgres 기동
service postgresql start

# 2. 전용 측정 인스턴스 기동 (공용 3400과 분리, 레이트리밋 상향)
cd apps/api && NODE_ENV=development PORT=3450 \
  RATE_LIMIT_GLOBAL_MAX=100000 RATE_LIMIT_AUTH_MAX=1000 \
  DATABASE_URL=postgresql://wooriai:wooriai_dev_password@localhost:5432/wooriai_dev \
  npx tsx src/main.ts &

# 3. 측정 (기본 N=200, 동시성 10)
LOAD_BASE_URL=http://localhost:3450 node scripts/qa/load-smoke.mjs

# 3b. 볼륨 축 ① 지출 (GAP-060 #8) — 대상 아이에게 이번 달 지출 N행을 심고 재측정.
#     전량 루프·깊은 커서 시나리오는 이때만 붙는다. 측정 후 자동 하드 삭제
#     (LOAD_SEED_KEEP=1이면 남긴다). 시드는 dev DB 전용 — 테스트 DB면 거부한다.
LOAD_BASE_URL=http://localhost:3450 LOAD_SEED_ROWS=5000 node scripts/qa/load-smoke.mjs

# 3c. 볼륨 축 ② 카탈로그 (GAP-067 #9) — 준비템 N개 + 각각 링크 M개를 심고 재측정.
#     상세·어드민 목록 시나리오는 시드 없이도 붙는다(기준선이 먼저 필요하다).
#     정리는 표식(item_templates.code = "load_smoke_seed_*") 기반 하드 삭제 —
#     클릭 → 상태 → 링크 → 준비템 순서이고 스테이지는 FK CASCADE로 함께 지워진다.
LOAD_BASE_URL=http://localhost:3450 LOAD_SEED_ITEMS=1000 LOAD_SEED_LINKS_PER_ITEM=3 \
  node scripts/qa/load-smoke.mjs

# 파라미터 조절: LOAD_N, LOAD_CONCURRENCY, LOAD_WARMUP, LOAD_SEED_ROWS,
#               LOAD_SEED_ITEMS, LOAD_SEED_LINKS_PER_ITEM,
#               LOAD_SEED_KEEP, LOAD_SEED_DATABASE_URL
# 끝나면 3450 인스턴스는 종료할 것.
```

> 두 시드 축 모두 **dev DB 전용**이다 — `wooriai_test`를 가리키면 스크립트가 거부한다(테스트 DB는
> vitest globalSetup의 자산이라 남의 스위트를 깨뜨린다). `LOAD_SEED_KEEP=1`이면 남기고, 그 상태로
> 다시 돌리면 다음 실행이 표식으로 먼저 걷어낸다.
>
> 시드 축은 POST 시나리오가 남기는 툼스톤(공개 API DELETE = 소프트 삭제)도 함께 하드 삭제한다.
> 그렇게 하지 않으면 반복 측정마다 툼스톤이 쌓이고 /sync/changes 델타가 실제보다 무거워진다
> (라운드 60에서 실제로 1,050건이 쌓여 있었다).

공용 dev 서버(3400)를 그대로 겨냥하면 전역 레이트리밋(300req/min)에 걸려 429가 섞이므로,
깨끗한 수치가 필요하면 반드시 전용 인스턴스를 쓴다. 429는 표에서 err와 분리 집계된다.
